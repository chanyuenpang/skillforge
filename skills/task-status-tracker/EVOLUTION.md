# Task Status Tracker 进化规则

本文件定义了 Task Status Tracker 技能的自我提升和进化机制。

## 核心理念

**好的进度跟踪，让用户安心，让自己高效。**

任务状态跟踪不仅是技术功能，更是用户体验的重要组成部分。准确的时间估计、及时的进度更新、清晰的任务状态，都是建立用户信任的关键。

---

## Review → Apply → Report 循环

这是 Task Status Tracker 持续改进的核心循环。

### 1. Review（任务开始前回顾）

**在注册任务之前，问自己：**

```
1. 这个任务需要状态跟踪吗？
   - 预计耗时超过 1 分钟？
   - 用户可能中途询问进度？
   - 需要异步执行？

2. 如何估算时间？
   - 查看 .learnings/LEARNINGS.md 中的历史数据
   - 类似任务的实际耗时是多少？
   - 需要预留多少缓冲时间？

3. 进度如何划分？
   - 任务可以分成几个阶段？
   - 每个阶段的里程碑是什么？
   - 如何向用户描述每个阶段？
```

**检查历史记录：**
- 查看 `.learnings/LEARNINGS.md` 中类似任务的耗时估计
- 查看 `.learnings/ERRORS.md` 避免已知的估计错误
- 参考 `SKILL.md` 中的最佳实践

### 2. Apply（执行并监控）

**注册任务：**
```javascript
// 1. 生成任务ID
const taskId = `task-${date}-${seq}`;

// 2. 创建任务状态文件
{
  "taskId": "task-20260314-001",
  "status": "running",
  "progress": 0,
  "createdAt": "2026-03-14T10:00:00Z",
  "estimatedCompletion": "2026-03-14T10:05:00Z",
  "updates": []
}
```

**启动 Subagent：**
```javascript
sessions_spawn({
  prompt: "执行任务并更新进度",
  deliver: false
})
```

**进度更新策略：**
| 任务阶段 | 进度范围 | 更新频率 |
|----------|----------|----------|
| 初始化 | 0-10% | 一次 |
| 数据准备 | 10-30% | 每完成一个子任务 |
| 核心处理 | 30-80% | 每完成一个里程碑 |
| 收尾工作 | 80-100% | 完成后更新 |

### 3. Report（任务完成后汇报）

**评估时间估计准确性：**
```
实际耗时 vs 预估耗时 = 估计偏差率

偏差率 < 20% → 优秀，记录成功策略
偏差率 20-50% → 可接受，分析原因
偏差率 > 50% → 需要改进，记录到 ERRORS.md
```

**评估进度展示效果：**
```
用户是否主动询问过进度？
├── 是 → 是否因为更新不及时？
│   ├── 是 → 记录到 ERRORS.md（更新频率不足）
│   └── 否 → 用户只是关心，正常
└── 否 → 进度展示清晰，用户安心
```

**记录学习：**
- **成功**：记录到 `LEARNINGS.md`
  - 任务类型和规模
  - 时间估计策略
  - 进度划分方法
  - 为什么有效

- **失败**：记录到 `ERRORS.md`
  - 估计偏差分析
  - 失败原因
  - 改进建议

- **改进想法**：记录到 `FEATURE_REQUESTS.md`
  - 更好的时间估计方法
  - 更清晰的进度展示
  - 自动化工具需求

## 触发器（Triggers）

什么时候记录学习？

### LEARNINGS.md 触发器

| 场景 | 记录内容 |
|------|----------|
| 时间估计准确（偏差 < 20%） | 任务特征 + 估计策略 + 成功因素 |
| 进度更新策略有效 | 阶段划分 + 更新频率 + 用户反馈 |
| 发现新的任务分解方法 | 分解策略 + 适用场景 + 优势 |
| 跨多个任务发现成功模式 | 模式总结 + 可复用性评估 |

### ERRORS.md 触发器

| 场景 | 记录内容 |
|------|----------|
| 时间估计偏差 > 50% | 预估 vs 实际 + 偏差原因 + 改进方法 |
| 用户频繁询问进度 | 更新频率问题 + 用户期望分析 |
| 进度更新不及时 | 更新机制问题 + 技术原因 |
| 任务状态丢失或损坏 | 数据问题 + 恢复过程 + 预防措施 |
| 用户对进度展示不满意 | 反馈内容 + 展示问题 + 改进建议 |

### FEATURE_REQUESTS.md 触发器

| 场景 | 记录内容 |
|------|----------|
| 用户想要更好的进度可视化 | 需求描述 + 优先级 |
| 需要自动化时间估计 | 功能描述 + 实现思路 |
| 希望增加任务预警机制 | 使用场景 + 价值分析 |
| 需要更好的历史数据分析 | 需求描述 + 数据来源 |

## 时间估计改进

### 历史数据分析

**记录每次任务的关键数据：**
```json
{
  "taskType": "file_analysis",
  "dataSize": "1GB",
  "estimatedTime": "300s",
  "actualTime": "420s",
  "deviation": "+40%",
  "complexityFactors": ["large_file", "complex_parsing"],
  "lessons": "大文件分析需要预留更多时间"
}
```

### 时间估计公式

**基础公式：**
```
预估时间 = 基准时间 × 复杂度系数 × 风险系数

其中：
- 基准时间：根据历史数据或经验估算
- 复杂度系数：1.0（简单）/ 1.5（中等）/ 2.0（复杂）
- 风险系数：1.0（确定）/ 1.3（不确定）/ 1.5（高风险）
```

**任务类型基准参考：**
| 任务类型 | 基准时间范围 | 复杂度因素 |
|----------|--------------|------------|
| 文件读取/分析 | 1s - 30s | 文件大小、格式复杂度 |
| 批量处理 | 10s - 5min | 数据量、处理逻辑 |
| 网络请求 | 1s - 10s | 响应速度、重试次数 |
| 代码生成 | 5s - 2min | 复杂度、语言类型 |
| 数据分析 | 10s - 10min | 数据量、算法复杂度 |

### 渐进式改进

**从偏差中学习：**
```
如果偏差 > 50%：
  → 记录到 ERRORS.md
  → 分析根本原因
  → 调整该任务类型的基准时间
  → 下次使用新基准

如果偏差 20-50%：
  → 记录到 LEARNINGS.md
  → 分析影响因素
  → 调整复杂度或风险系数

如果偏差 < 20%：
  → 记录到 LEARNINGS.md（成功案例）
  → 保持当前策略
```

## 提升规则（什么时候提升到主文档？）

### 提升决策树

```
是否出现了 3 次以上？
├── 是 → 提升到 SKILL.md 或 AGENTS.md
│   │
│   └── 类型判断：
│       ├── 时间估计策略 → SKILL.md「最佳实践」
│       ├── 进度展示方法 → SKILL.md「使用场景」
│       ├── 任务跟踪流程 → AGENTS.md
│       └── 工具使用技巧 → TOOLS.md
│
└── 否 → 是否跨 2 个不同任务出现？
    ├── 是 → 考虑提炼成通用模式
    │
    └── 否 → 用户是否特别强调要记住？
        ├── 是 → 立即提升到 MEMORY.md
        └── 否 → 保留在 .learnings/ 中继续观察
```

### 提升目标表

| 学习类型 | 提升到 | 示例 |
|----------|--------|------|
| 时间估计策略 | `SKILL.md` | "大文件分析预留 1.5x 时间" |
| 进度展示最佳实践 | `SKILL.md` | "每 20% 更新一次进度" |
| 任务跟踪流程 | `AGENTS.md` | "注册→执行→更新→完成的完整流程" |
| 状态文件格式 | `SKILL.md` | "标准 JSON 结构" |
| 重要经验原则 | `MEMORY.md` | "用户关心的是进度，不是技术细节" |
| 核心理念 | `SOUL.md` | "好的进度跟踪让用户安心" |

### 提升检查清单

在提升之前，确保：

- [ ] 该学习已经验证有效（至少 2 次成功应用）
- [ ] 描述清晰，没有歧义
- [ ] 包含具体的应用场景
- [ ] 有明确的操作步骤或决策标准

## 定期回顾机制

### 每周回顾（建议每周五）

1. **检查未处理的学习记录**
   - 查看 LEARNINGS.md 中 status = pending 的条目
   - 查看 ERRORS.md 中 status != resolved 的条目

2. **评估提升候选**
   - 统计重复出现的学习
   - 标记应该提升到主文档的内容

3. **更新优先级**
   - 根据影响范围调整 priority
   - 标记已解决的问题

### 每月复盘

1. **生成学习报告**
   - 本月新增多少学习记录？
   - 时间估计准确率变化趋势？
   - 提升到主文档的内容有哪些？

2. **流程改进**
   - 当前的任务跟踪流程是否高效？
   - 进度展示是否满足用户需求？
   - 需要更新 SKILL.md 吗？

- [ ] 预计完成时间是否合理？
- [ ] 状态文件路径是否正确？

- [ ] 进度百分比是否合理？
- [ ] 状态描述是否清晰？
- [ ] 更新时间是否及时？
- [ ] 用户是否能理解当前状态？

- [ ] 最终状态是否正确？
- [ ] 是否有结果摘要？
- [ ] 是否需要通知用户？
- [ ] 是否需要归档或清理？
