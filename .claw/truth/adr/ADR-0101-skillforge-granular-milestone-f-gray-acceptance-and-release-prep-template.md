# ADR: SkillForge 里程碑 F 灰度验收与发布准备模板

## Status

accepted

## Context

里程碑 F 的完成结果已经把灰度验收从一次性检查变成了可复用的发布准备面：通过将灰度验收拆成 `flow-01` / `flow-02` / `flow-03` 三条真实业务流，并同步产出发布说明草案，子计划从“验证可行”推进到“可发布前验收”。

计划复盘同时暴露了两个长期问题：一是如果不把验收流固化成模板，后续同类子计划会继续出现前置覆盖盲区；二是如果没有统一的结果摘要，放量建议、回滚阈值和风险等级就很难稳定对外表达。

## Decision

决定将里程碑 F 这类灰度子计划收口为固定模板：

1. **默认以三条验收流组织灰度验证**
   - 灰度验收基线默认从 `flow-01` / `flow-02` / `flow-03` 起步，而不是只靠单条脚本或临时补流。
   - 当某条流的关键结论后置固化时，应优先把风险转成新的验收流，而不是只停留在讨论层。

2. **发布说明草案必须与验收同步产出**
   - 发布说明不再作为收尾附录，而是与验收进展并行推进。
   - 草案至少要覆盖已完成范围、真实业务流、上线闸门和已知限制，避免“技术已完成、发布材料滞后”。

3. **统一灰度验收结果摘要字段**
   - 后续同类子计划应固定输出一页式摘要，至少包含：流状态、风险等级、放量建议、回滚阈值、责任人。
   - 这份摘要是发布决策输入的一部分，不只是内部记录。

4. **在下一里程碑启动前增加验收覆盖评审**
   - 在进入新里程碑前先检查当前验收流覆盖是否足够，提前补建缺口，减少后补成本。

## Alternatives Considered

- **继续按项目临时决定验收流数量**：拒绝。会反复出现补位式建设，难以稳定复用。
- **只记录通过结果，不沉淀摘要模板**：拒绝。放量建议和回滚阈值会失去统一表达。
- **把发布说明放到最后再写**：拒绝。容易再次出现发布材料滞后。

## Consequences

- 正向：后续同类灰度子计划可以直接复用“三流起步 + 同步发布说明 + 一页式摘要”的结构。
- 正向：风险判断更容易落到可执行的放量建议和回滚阈值上。
- 正向：验收流覆盖评审能更早暴露盲区，减少临时补位。
- 取舍：子计划前期成本会更高，因为要先准备完整验收面和摘要。
- 风险：如果后续只补技术结论，不同步维护摘要字段，模板会退化成空壳。
- 验证锚点：本次复盘已确认三条关键验收流全部通过，发布说明草案同步更新，且子计划达到 `end.completed`。
