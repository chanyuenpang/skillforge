# ADR: SkillForge 商业级 100% 目标重锚与完成定义冻结

## Status

accepted

## Context

当前主计划不再以 MVP 或可演示形态为目标，而是重新锚定到“商业级可用、实际可用、可发布、可运营、可扩展”的 100% 产品落地。此前已有多轮阶段推进与里程碑收口，但如果没有一个更高层级的完成定义，后续规划仍可能被局部能力、阶段性收口或短期可交付状态牵着走。

这次计划进一步明确：在主目标不变的前提下，现场验收不能停留在口头结论或子任务汇报，必须由主 Agent 本人使用 `browseros-cli` 直接查看真实页面、只围绕单一主判断句推进，并按“现场看页面 -> 识别唯一缺口 -> 只修这一缺口 -> 再现场验收”的闭环推进。

## Decision

SkillForge 的主计划目标固定为商业级 100% 产品落地，而不是 MVP 或仅可演示版本。

具体约束如下：

1. **目标重锚到商业级产品**
   - 主计划的最终目标必须表达为商业级可用、实际可用、可发布、可运营、可扩展。
   - 后续所有阶段规划、任务拆解和验收口径，都必须以这个终态为基准。

2. **完成定义冻结**
   - 主计划必须明确写出完成定义、验收口径与不可接受状态。
   - 不能只写实现清单，必须让目标能指导后续所有规划。

3. **先重锚，再推进**
   - 在进入实施前，必须先完成现状与目标差距盘点，并设计通往 100% 的阶段路线图。
   - 第一阶段实施计划必须建立在该路线图之上，不能偏离商业级总目标。

4. **持续回看最终目标**
   - 后续每一步执行前都要回看最终目标，避免围绕局部能力打转。
   - 主计划不再以局部完成作为阶段终点，而以是否逼近商业级终态作为判断基准。

5. **现场验收必须由主 Agent 直看真实页面**
   - 现场验收必须使用 `browseros-cli` 在真实页面上完成，不允许用子任务口头结论替代。
   - 任何一次验收都只允许围绕一个主判断句推进：用户在真实页面看到的内容不能是 JSON 本体，而且内容本身要有实际价值。
   - 推进方式固定为单缺口闭环：先看真实页面，再识别唯一缺口，只修这一点，然后再次现场验收。

## Alternatives Considered

- 继续沿用 MVP 目标：被拒绝。MVP 只能约束最小可用范围，无法表达商业级落地要求。
- 只做当前阶段的功能收口：被拒绝。这样容易在局部完成后停滞，无法形成 100% 路线。
- 直接进入实施而不先冻结完成定义：被拒绝。缺少统一完成定义会导致后续阶段验收口径漂移。

## Consequences

- 正向：后续所有规划与验收都将围绕商业级 100% 终态展开，不会再以 MVP 作为默认目标。
- 正向：完成定义被冻结后，后续阶段的输入、验收和边界更清晰，减少方向漂移。
- 正向：先做差距盘点和路线图设计，可以让第一阶段实施直接对齐商业级终态。
- 正向：现场验收改为主 Agent 直看真实页面后，口头结论和实际页面状态之间的偏差更难混入流程。
- 取舍：目标越高，前期规划成本越大，不能再用碎片化任务代替整体路线。
- 风险：如果后续任务只完成局部实现而不持续回看终态，仍可能回到局部最优。
- 风险：若没有持续使用 `browseros-cli` 做现场验收，仍可能误把推断当成通过。
- 验证锚点：主计划已明确要求第一阶段前先完成 gap list 与 100% 路线图，再进入实施；现场验收则必须以真实页面可见事实为准。
