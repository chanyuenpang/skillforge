# ADR-0096: SkillForge Web UI 全面美化与体验优化里程碑

## Status

proposed

## Context

`RunCenter` 的核心功能链路已经打通，但用户反馈明确指出：当前页面虽然可用，还不够像一款真正的产品。现有页面仍偏工程面板风格，视觉层次、信息节奏、空态/加载态、微交互与响应式基础都需要系统收口。

这次里程碑不是新增业务能力，而是把既有的 `overview`、`list`、`detail` 三页按统一产品标准做全面美化与体验升级。计划记录还明确要求采用 `SkillForge` 标准流程：先做全局 UI 审计与参考方向确认，再分阶段实施，再逐阶段验收。

## Decision

决定将 `SkillForge Web UI` 的本轮收口定义为一个长期里程碑，遵循以下规则：

1. **先审计，再美化**
   - 必须先完成全局 UI 审计，确认当前最影响美观与好用度的问题，再进入实现。
   - 审计应覆盖 `overview`、`list`、`detail` 三页在布局比例、间距、色彩层次、字体层级、卡片/表格/按钮视觉、空态/加载态/错误态、导航与返回链、移动端基础响应上的问题。

2. **以统一视觉基础作为底座**
   - 视觉升级优先从 `tokens.css`、布局壳、卡片、按钮、表格、标签等基础层收口。
   - 目标不是局部修饰，而是让三页共享同一套现代产品质感。

3. **先理信息架构，再做细节装饰**
   - `overview`、`list`、`detail` 的信息密度与阅读节奏必须重新组织，重要内容前置，技术信息后置。
   - 页面节奏、导航与返回链要统一，避免用户在不同页面感受到割裂。

4. **非正常状态必须有产品化表达**
   - 空态、加载态、错误态、无权限态不能再退化为技术空白页。
   - 这些状态必须具备引导、说明和可操作入口。

5. **细节打磨要建立在前面两层之上**
   - 动画、微交互、hover/focus、展开折叠反馈、移动端基础断点属于最后一层收口。
   - 允许有局部渐进，不做完整移动端重构。

6. **验收必须覆盖真实三页体验**
   - 最终验收要覆盖 `overview`、`list`、`detail` 的完整视觉与交互体验。
   - 只看代码层通过不够，必须确认用户真的会觉得“好用且美观”。

## Alternatives Considered

- **只做视觉修饰，不改信息层级**：拒绝。这样只能变漂亮一点，不能解决“像工程面板”的根因。
- **先做新功能再来美化**：拒绝。当前问题不是能力不足，而是体验与产品感不足。
- **只修某一个页面**：拒绝。三页之间风格不统一会让产品感继续碎片化。
- **直接上大规模重构**：拒绝。与计划目标不符，也会把已有的人类可读化成果冲掉。

## Consequences

- 正向：`overview`、`list`、`detail` 将从“能用”升级到统一的产品级观感。
- 正向：用户会先看到清晰的层次、节奏和可读性，而不是工程面板式堆叠。
- 正向：空态、加载态、错误态会变成可理解、可操作的产品状态。
- 取舍：实现会比单点修补更关注统一性，因此局部改动必须服从整体视觉规范。
- 取舍：细节交互会增加一定前端维护成本，但能显著降低粗糙感。
- 验证锚点：计划已明确安排“全页面美化收口验证”，后续验收应以三页实际体验为准。
