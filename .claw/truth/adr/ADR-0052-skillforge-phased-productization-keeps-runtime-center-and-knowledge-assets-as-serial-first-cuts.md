# ADR: SkillForge phased productization keeps runtime center and knowledge assets as serial first cuts

## Status

accepted

## Context

在完成产品总纲、网页 IA、路线治理和双子域 spec 之后，下一阶段不再是继续补文档，而是把 SkillForge 从“文档规格完整”推进到“产品模块真正可用”。

这次阶段计划给出的稳定结论是：运行中心与知识资产都要进入网页端和接口层的最小可操作闭环，但第一阶段必须先把**运行中心只读闭环**做出来，再做**知识资产只读闭环**。计划里还确认了当前真实可用链路集中在审批域，`run` / `knowledge` 目前都缺少专属 API，因此第一阶段只能从 `web-server.mjs` 新增只读端点起步，不能把两个域并行摊开做。

## Decision

决定将 SkillForge 第一阶段产品化固定为**串行第一刀**策略：先做运行中心只读闭环，再做知识资产只读闭环，最后再考虑跨域打通与扩展。

具体约束如下：

1. **先建立阶段计划，再拆子计划推进**  
   第一阶段不把所有实现打包成一个大任务，而是先有阶段计划，再分别为运行中心和知识资产建立独立子计划。

2. **运行中心优先落地只读第一刀**  
   运行中心先完成网页端与接口层的只读最小闭环，优先收敛 `\`/run-center\`、`\`/run-center/runs\`、`\`/run-center/runs/:runId\`` 与 3 个只读聚合端点，先证明不是占位页。

3. **知识资产随后串行推进只读第一刀**  
   知识资产在运行中心落地后再推进第一刀，优先收敛 `\`/knowledge-assets\`` 与 `\`/knowledge-assets/:assetId\`` 的只读闭环，数据优先来自真实文档目录扫描。

4. **共享基础件必须保持一致**  
   两条线共享的基础件包括 `web/`、`web-server.mjs`、导航入口、占位页调整，以及运行对象字段与 API 契约的一致性约束；这些部分必须避免并行修改。

5. **跨域打通放在阶段后段**  
   等两个子计划各自成形后，再做跨域打通与验证，不提前把联动复杂度塞进首刀实现。

## Alternatives Considered

- 运行中心和知识资产并行做第一刀：拒绝。会在导航、状态承载位和接口契约上互相干扰。
- 先把两个域都写成大而全的实现计划：拒绝。会破坏阶段计划的可执行性，难以按顺序派发。
- 继续停留在文档规格层，不进入产品化：拒绝。当前阶段的目标已经明确要求从规格走向可用闭环。

## Consequences

- 正向：阶段推进顺序清晰，运行中心和知识资产不会在同一区域同时开工。
- 正向：共享的导航和状态承载位可以先稳定下来，减少后续返工。
- 正向：先把只读闭环做出来，后续再扩展写操作或更深层联动时更容易控制风险。
- 取舍：阶段完成速度会比并行推进慢一些，但能换来更低的耦合风险。
- 风险：如果子计划边界定义不清，串行策略仍可能在后续跨域打通时暴露耦合问题。
- 验证锚点：先完成运行中心第一刀只读产品化，再进入知识资产第一刀只读产品化，最后再做跨域打通与验证。
