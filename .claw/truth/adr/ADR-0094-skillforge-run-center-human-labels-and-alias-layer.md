# ADR: SkillForge RunCenter 人类标签与别名层收口

## Status

accepted

## Context

RunCenter 前两轮已经把主视图从“机器字段罗列”推进到“人类原话优先、摘要兜底”和“首页/详情页的可观测性增强”。但这次计划进一步暴露出一个更长期的问题：即使内容本身变得可读，页面里仍有不少 `fixture`、`source`、`requestId` 之类的机器术语直接顶在主叙事位，普通用户仍需要先翻译术语，才知道页面在讲什么。

因此，这次收口不再只关心输入输出是否可读，而是把运行中心的信息架构再往前推一步：主视图应以人类能记住、能理解的标签和别名为先，内部标识只作为辅助定位信息保留。

## Decision

决定在 `RunCenterOverview`、`RunCenterList`、`RunCenterDetail` 三个页面统一采用以下长期规则：

1. **主叙事位优先使用人类标签**
   - 页面标题、字段标题、说明文本、列表主列应优先使用更稳定、可记忆、可理解的人类标签。
   - `fixture`、`source`、`requestId` 等内部术语不得直接占据主叙事位，除非用户明确需要排障视角。

2. **机器术语降级为别名或辅助说明**
   - 若必须保留内部字段名，应放入次要信息区、技术区或补充说明中，并同时给出人类解释。
   - 同一信息应优先展示“人类标签 + 必要时的机器别名”，而不是“机器名词 + 无解释”。

3. **三页面使用同一套标签语义**
   - `RunCenterOverview`、`RunCenterList`、`RunCenterDetail` 对同一概念必须保持一致的标签与别名，不允许同一信息在不同页面换一套说法。
   - 可读性优先于字段原样暴露；若标签需要区分业务与技术语境，应通过辅助文案解释，而不是把内部名词顶上来。

4. **允许保留定位能力，但不牺牲理解成本**
   - 机器 ID、内部来源、请求标识等仍可用于定位和追踪，但只能作为辅助信息存在。
   - 用户浏览运行中心时，应该能凭页面标签理解内容，而不依赖记忆内部 ID 或系统术语。

5. **实施方式优先复用现有数据层**
   - 优先通过前端文案、标签映射、辅助说明和视觉层次调整实现人类化。
   - 不先推动后端存储模型重构；只有当现有字段长期无法支撑统一标签时，才另开后端协议或数据结构任务。

## Alternatives Considered

- **继续让 `fixture`、`source`、`requestId` 直接作为主展示名**：拒绝。会继续把机器术语放在主叙事位，违背运行中心面向人的目标。
- **只在某一页做标签优化**：拒绝。三页面如果语义不一致，用户还是要在页面之间重新翻译。
- **先重构后端数据模型再改前端**：拒绝。当前主要问题是展示层的术语层级，不需要先承担更大的协议改造成本。

## Consequences

- 正向：运行中心三页面会更像给人看的产品，而不是给系统排障的面板。
- 正向：同一概念在 overview/list/detail 中保持一致，降低理解和记忆成本。
- 正向：内部 ID 仍可保留为辅助定位锚点，不影响追踪能力。
- 取舍：前端需要维护一层标签映射与别名规则，展示逻辑会比直接字段透出更复杂。
- 取舍：若后续增加新的内部术语，也需要同步纳入标签层，否则可读性会回退。
- 验证锚点：本次计划的验收目标已明确要求检查三页面是否不再把 `fixture/source/requestId` 等机器术语顶到主叙事位。
