# ADR: L2 真实验证切片与 verdict 边界

## Status

accepted

## Context

L2 子计划已经完成负责人级收口，但收口的不是最终 verify 结果，而是“真实验证执行骨架”。这一步的价值在于：先把门禁负例、Run 版本防漂移、证据可回看、对象链连续性以及综合 verdict 的职责边界固定下来，避免后续真正派发 verify-agent / 审查型子任务时再次把验证、裁决和回退口径混在一起。

## Decision

决定将 L2 固化为“真实验证切片 + verdict 独立边界”的执行骨架，并按以下规则推进：

1. 第一波真实验证优先覆盖四类切片：门禁负例、版本防漂移、证据回看、对象链连续性。
2. `verify` 类任务与 `verdict` 类任务必须拆开，综合 verdict 不能揉进单一验证任务里。
3. 验证切片与裁决任务要明确依赖顺序、并行窗口和回退口径，后续派发要直接沿用这套边界。
4. `V1`、`V2` 作为硬前置，`V3`、`V4` 作为并行验证窗口，`D1` 作为独立收口点。
5. L2 当前完成的是执行骨架定版，不代表 `verify` 卡、综合 verdict 与回退口径已经真实跑出结果。

## Alternatives Considered

- 直接把 L2 当成真实验证已完成：被放弃，因为当前完成的是执行骨架，不是实际验证结果。
- 把 `verify` 和 `verdict` 合并成一个任务：被放弃，因为会破坏审计边界、独立裁决和回退口径。
- 不提前固定依赖顺序与阶段禁区：被放弃，因为后续派发会再次失去结构约束。

## Consequences

- 正向：后续真实验证可以直接按切片和职责边界派发，不必重新发明任务结构。
- 正向：`verify` 与 `verdict` 分离后，审计、回退和复核会更清晰。
- 正向：`V1/V2/V3/V4` 与 `D1` 的顺序和并行关系被固定，利于稳定执行。
- 取舍：这次沉淀的是骨架定版，不等于真实验证结果已经完成。
- 风险：如果后续执行重新把验证与裁决揉合，L2 的收口价值会迅速衰减。
