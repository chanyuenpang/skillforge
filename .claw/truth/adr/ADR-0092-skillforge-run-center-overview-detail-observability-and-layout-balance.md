# ADR: SkillForge RunCenter 首页权重平衡与详情可观测性增强

## Status

accepted

## Context

`/run-center` 首页原先出现主次失衡：左侧“最近运行”承担信息主体，但列宽和卡片厚度不足；右侧“下一步入口”视觉权重过重，压缩了最近运行的可读性。与此同时，`RunCenterDetail` 详情页主要依赖少数摘要字段，导致成功/失败记录虽然已有结构化内容，却常常只显示“摘要不可用”，用户看不到输入、输出、错误、日志、证据等关键上下文。

这次二轮优化先核查了现状，再把问题收敛为两个长期可复用的前端规则：首页信息层级必须重新平衡，详情页必须优先消费结构化字段并提供可观测分区，而不是只展示单一摘要。

## Decision

决定对 SkillForge RunCenter 采用以下长期前端策略：

1. **首页采用左主右辅的布局权重**
   - `RunCenterOverview` 中“最近运行”必须作为主信息区，获得更大的可读宽度。
   - 右侧“下一步入口”只能作为辅助区，降低卡片厚度与视觉压迫感。
   - 最近运行表格优先保留 `runId`、状态、来源、时间等核心列，并为关键列设置最小宽度，必要时允许横向滚动保护窄屏可读性。

2. **详情页必须优先提取结构化字段而不是只依赖摘要**
   - `RunCenterDetail` 的摘要兜底链必须覆盖更多候选字段，避免把已有结构化记录降级成“摘要不可用”。
   - 详情页应按语义分区展示输入、输出、错误、日志、证据等信息，而不是把所有内容压成单一文本块。
   - 对于元数据如 `endedAt`、`riskType`、`severity`、`transcriptCount`、`attempt`、`retryCount`、`version` 等，应在可观测区直接展示，帮助用户快速判断运行状态与失败线索。

3. **优先复用现有 API 数据，不先升级后端协议**
   - 前端应先通过字段分组、摘要兜底和结构化展示提升可读性。
   - 只有当真实运行记录长期缺字段、且前端确实无法满足观测需求时，才另开后端任务补协议。

4. **回归验证必须覆盖首页与详情页两类样本**
   - 首页要验证最近运行重新成为主信息区。
   - 详情页要验证成功/失败记录都能看到输入、输出、错误、日志、证据中的可用内容。
   - 仅做代码层验证不够，后续产品验收应补浏览器实跑与真实样本证据。

## Alternatives Considered

- **只做视觉修饰，不改信息层级**：拒绝。这样无法解决“最近运行被压窄”和“详情页看不到内容”的实质问题。
- **优先要求后端新增协议字段**：拒绝。当前前端已能从现有返回中提取到足够多的结构化信息，先做前端增强见效更快。
- **继续只显示摘要文本**：拒绝。会延续“摘要不可用”的问题，无法满足成功/失败记录的可观测性要求。

## Consequences

- 正向：`/run-center` 首页的“最近运行”重新成为主信息区，可读性明显提升。
- 正向：`RunCenterDetail` 能直接展示输入/输出/错误/日志/证据等结构化内容，不再只剩摘要。
- 正向：在不改后端协议的前提下，前端即可显著提升运行记录的可观测性。
- 取舍：当前实现仍偏前端层，真实产品验收最好补浏览器实跑与截图级证据。
- 取舍：布局优化采用组件内局部样式策略，后续若继续演进，可再回收为更体系化样式。
- 验证锚点：开发实现层面已完成 `build` 与服务重启，回归确认旧路由兼容、首页重排和详情分区均成立。
