# SkillForge 长期演进路线与文档体系治理规则（v1）

## 1. 文档目的与适用范围

本文档用于统一 SkillForge 在未来 12 个月内的**产品演进节奏**与**文档治理方式**，解决以下问题：

- 在"底层能力相对完整、上层产品定义刚补齐、Web 壳层已建立但模块深度不足"的现实下，如何分阶段推进；
- 如何避免 roadmap、IA、spec、ADR、feature truth、phase 报告之间职责重叠、冲突或失真；
- 如何在不夸大承诺的前提下，形成"可验证、可追溯、可迭代"的产品治理闭环。

适用范围：

- SkillForge 产品与工程的中长期规划；
- `docs/` 下产品与架构类文档；
- `.claw/truth/` 下事实状态、能力状态、交付状态文档；
- 各阶段产出（phase 报告、专项 spec、ADR、feature 记录）。

不适用范围：

- 单次临时活动记录（如会议纪要草稿）；
- 与 SkillForge 无直接耦合的外围工具细节实现文档。

## 2. SkillForge 未来 12 个月阶段化演进路线

> 路线原则：先"可见可控"，再"规模化与智能化"；先打通纵向闭环，再扩展横向能力面。  
> 时间为目标窗口，不构成硬性交付承诺；每阶段以进入/退出条件判定，而非日期到点自动切换。

### 阶段 A（0-3 个月）：定义收敛与最小闭环固化

定位：把"已有底层能力"转为"用户可理解、可执行、可验证"的最小产品闭环。

重点：

- 固化产品总纲、Web IA、核心模块边界；
- 完成风险审批、运行中心、对象追溯的最小可用链路定义；
- **任务编排初定义**：PromptDraft 与 StepPlan 的结构化模板落地，确立“编排在前、审批在中、执行在后”的流程骨架；
- **Skeleton 结构规范**：定义 workflow skeleton 的要素规范（目标 / 阶段 / 检查点 / 产物），作为知识资产域的基类结构；
- 建立文档分层与变更归档机制，停止"同一事实多处写法不一致"。

### 阶段 B（3-6 个月）：运行可观测与治理机制成型

定位：从"能跑"升级到"可治理"，让运营、研发、管理三方可共享同一状态视图。

重点：

- 运行中心从页面壳层走向可操作工作台；
- **任务编排从静态模板升级为可编辑 / 可提交 / 可追溯**的基础工作台，PromptDraft 编辑与 StepPlan 拆解形成独立操作路径；
- **Skeleton 库原型落地**：支持创建、选择与应用结构化计划骨架，skeleton → StepPlan 的半自动转化链路可用；
- 审批与执行过程具备可追溯证据链；
- 知识与资产管理进入标准化（结构、标签、版本）；
- 配置与系统能力开始纳入受控发布流程。

> 阶段一当前事实：运行中心与知识资产第一刀已完成，均已形成只读闭环并通过非占位验证。运行中心当前验证到的是 execution-log 为空时的真实空数据闭环；知识资产当前验证到的是 `docs/` + `fixtures/` 白名单来源下的真实只读闭环，其中 doc 详情 happy path 已实测，skill-fixture 详情分支代码已实现但尚未补第二条命令样例抽测。

### 阶段 C（6-9 个月）：跨域联动与资产复用深化

定位：打破模块孤岛，形成任务—编排—审批—执行—复盘—知识沉淀的连续流。

重点：

- 对象 registry 建立跨域引用规范；
- **PromptDraft 与 StepPlan 从“一次性任务对象”升级为可引用资产**，支持跨任务模板化复用；
- **Skeleton 与执行记录联动**，支持从执行回放 → 复盘 → 骨架修正的治理闭环；
- feature truth 与 phase 报告形成自动 / 半自动关联；
- 子域 spec 与 ADR 的触发边界稳定，减少"口头决策"；
- 关键能力从单项目可用走向多场景复用。

### 阶段 D（9-12 个月）：规模化演进与策略化优化

定位：在稳定治理前提下，推进规模化使用与策略层优化，不以"功能堆叠"为目标。

重点：

- 治理指标化（变更质量、文档一致性、追溯完整度、阶段目标达成率）；
- **编排策略探索**：基于历史执行效果，探索 prompt 优化建议与步骤推荐（辅助人工判断，非自动替代）；
- **Skeleton 质量评分与场景适配**：按任务类型标记适用范围，支持按场景筛选与效果反馈；
- 风险策略分层（默认策略、场景策略、例外机制）；
- 运行与知识系统联动优化（复盘驱动下一轮规划）；
- 为下一周期（12 个月后）留下清晰可继承基线。

## 3. 各阶段目标、可见产出、进入条件/退出条件

### 阶段 A：定义收敛与最小闭环固化

**阶段目标**

- 完成"产品叙事一致性"：产品总纲、IA、roadmap、truth 不互相矛盾；
- 明确核心对象与流程主干（任务、审批、执行、产出、归档）；
- **确立任务编排（prompt 优化 / 步骤化）与 skeleton 的结构定义**；
- 形成第一版文档治理规则并执行。

**可见产出**

- 更新后的产品总纲与 IA 分层文档；
- 核心能力域最小闭环说明（尤其审批、运行、registry）；
- **PromptDraft / StepPlan 初始结构定义文档**（字段、约束、与审批的前后关系）；
- **Skeleton 结构规范文档**（要素定义、最小必填字段、与 StepPlan 的映射关系）；
- 文档索引与变更入口（谁改什么、改到哪里）。

**进入条件**

- 产品总纲与 IA 初稿已完成；
- 现有底层能力可被事实性描述（不依赖未来假设）。

**退出条件**

- 核心术语与对象定义在主文档中统一；
- 至少一个端到端路径可在文档中闭环追溯（含 prompt 草案 → 步骤计划 → 审批 → 执行）；
- roadmap 中每项中期目标均能对应到至少一个文档承载位；
- PromptDraft 与 Skeleton 的结构定义已书面定稿。

---

### 阶段 B：运行可观测与治理机制成型

**阶段目标**

- 运行中心具备"查看状态 + 触发动作 + 查看结果"的基础可操作性；
- **任务编排形成独立可操作路径**：PromptDraft 编辑、StepPlan 拆解与提交；
- **Skeleton 库具备基本 CRUD 与任务应用能力**；
- 审批链路与执行证据链可被审计；
- 配置变更与行为变更开始受控。

**可见产出**

- 运行中心模块化说明与关键场景流（含任务编排子流）；
- 风险审批策略说明（默认策略与边界）；
- **Skeleton 库使用说明**（创建 / 应用 / 版本记录）；
- 配置项分类与变更流程文档；
- phase 报告模板及最小必填字段；
- 阶段一已形成的可演示产品面：总览、风险审批、运行中心、知识资产、设置五个顶层入口在同一壳层下共存，且 run-center / knowledge-assets 两条只读闭环已落地。

**进入条件**

- 阶段 A 的术语与对象模型稳定（含 PromptDraft、StepPlan、Skeleton）；
- 已有最小闭环运行样例可复用；
- 编排层与资产层原型可用（不要求生产级稳定性）。

**退出条件**

- 核心流程的"前置条件 / 动作 / 结果"可在统一视图中定位；
- 高风险动作有明确审批门禁与例外流程；
- **至少一个 Skeleton 可从创建 → 应用到任务 → 执行追溯的闭环可用**；
- 至少一轮 phase 报告可追溯至对应 feature truth 与 ADR（如有）。

---

### 阶段 C：跨域联动与资产复用深化

**阶段目标**

- 打通跨能力域对象引用，减少重复录入与信息漂移；
- 形成"改动→决策→编排→交付→复盘→沉淀"的标准链；
- 提高资产复用率与变更一致性；
- **PromptDraft / StepPlan 与 Skeleton 形成可关联可复用的治理闭环**。

**可见产出**

- registry 对象模型扩展与跨域引用规范；
- feature truth 与 phase 报告的映射关系规则；
- **编排对象与资产对象的关联规范**（PromptDraft ↔ Skeleton，Task ↔ ExecutionRun，ExecutionRun ↔ Skeleton 版本）；
- 子域 spec 的标准目录与完成定义（DoD）；
- ADR 触发清单（何时必须写、何时可选）。

**进入条件**

- 阶段 B 的治理流程已经稳定执行至少一轮；
- 主要模块存在可关联对象（而非纯静态页面）；
- Skeleton 库已可用且至少有一条任务应用记录。

**退出条件**

- 跨域对象关联在关键流程中可用；
- **从一次任务编排到执行到 skeleton 回沉的链路可追溯**；
- 重要变更可以从 phase 报告回溯至 feature 与决策依据；
- 重复定义与冲突描述显著下降（以文档巡检结果为准）。

---

### 阶段 D：规模化演进与策略化优化

**阶段目标**

- 在多场景下维持治理一致性；
- 从"流程可用"升级为"策略可优化、质量可度量"；
- **建设编排策略探索与 skeleton 质量反馈机制的基础设施**；
- 为下一年度路线形成可继承基线。

**可见产出**

- 治理指标面板定义（至少：一致性、追溯率、变更延迟、例外占比）；
- **编排效果反馈机制定义**（prompt 执行效果与步骤偏差记录）；
- **Skeleton 质量评分规则与适用范围标注**；
- 策略分层文档（默认/场景/例外）；
- 下一周期候选主题与风险清单。

**进入条件**

- 阶段 C 的跨域引用规范已在主要流程落地；
- 文档更新机制已能支撑持续演进；
- 编排与资产域已有可量化的使用数据（即便是少量）。

**退出条件**

- 指标可用于指导优先级调整，而非仅展示；
- **编排反馈数据可支撑人工决策（不要求自动优化）**；
- **Skeleton 质量评分规则已在至少一个任务类型上试用**；
- 文档体系可以支持外部协作方快速理解并执行；
- 下一年度路线已具备清晰起点与约束条件。

## 4. 各能力域的演进顺序与原则

> 顺序遵循"风险可控优先、执行可见优先、资产沉淀优先、平台扩展随后"的原则。  
> 不是线性串行，可并行推进，但优先级不可倒置。

1. **风险审批（优先级 P0）**  
   原因：没有风险门禁，后续任何规模化都不可控。  
   目标：先定义审批对象、风险等级、触发条件、例外机制，再扩展自动化能力。

2. **运行中心 —— 含任务编排（P0/P1）**  
   原因：必须让系统状态与动作可见，否则无法形成真实运营闭环；任务编排（prompt 优化 / 步骤化编排）是实现“可控执行”的必要入口——没有结构化编排，执行前的治理就无从落地。  
   目标：**阶段 A-B** 先统一状态视图和动作入口，并建立 PromptDraft / StepPlan 的最小可操作路径；**阶段 C** 将编排对象纳入可引用资产体系；**阶段 D** 探索基于历史数据的编排策略优化。

3. **对象追溯 / registry（P1）**  
   原因：没有对象身份与关系，文档与系统都无法稳定追溯。  
   目标：先建立核心对象唯一性与引用规则，再扩展跨域关系图（含编排对象 → 执行对象 → 资产对象的关联）。

4. **知识与资产 —— 含 Skeleton 资产化（P1/P2）**  
   原因：沉淀是长期复用的基础，但前提是对象与流程可追溯；workflow skeleton 作为结构化计划骨架，其价值在编排 → 执行 → 复盘闭环中才能体现，宜先定义后建设。  
   目标：**阶段 A** 先定义 Skeleton 结构规范与基础 CRUD；**阶段 B** 落地 Skeleton 库与任务应用链路；**阶段 C** 打通 Skeleton ↔ 执行记录的关联与复盘闭环；**阶段 D** 推进质量评分与场景化推荐。

5. **系统与配置（P2）**  
   原因：系统能力影响范围大，需在治理机制成熟后系统化推进。  
   目标：先配置分层与变更控制，再推进高级策略化编排。

## 5. 文档体系分层规则

### 5.1 产品总纲（Product Charter）

职责：

- 定义"我们做什么/不做什么"、目标用户、核心价值、能力边界；
- 给出阶段性战略方向与成功判据（非实现细节）。

不承载：

- 具体页面结构、字段细节、实现方案。

---

### 5.2 Web IA 设计（信息架构与模块分层）

职责：

- 定义页面层级、导航关系、模块职责与边界；
- 描述用户可见结构如何映射到能力域。

不承载：

- 底层技术决策细节；
- 单 feature 的业务规则全量定义。

---

### 5.3 子域 Spec（Domain/Module Spec）

职责：

- 对单一能力域给出完整规则：对象、流程、状态、约束、接口边界；
- 作为开发与验收的直接依据之一。

不承载：

- 跨域战略判断；
- 需要架构权衡的长期决策（应升格至 ADR）。

**当前与在途子域 Spec 承载位**

为支撑文档体系的完整性，以下子域 spec 应作为可辨识的独立文档承载位存在，无论其当前是已撰写、提纲态或在建：

| 子域 | 对应 spec 承载位 | 覆盖范围 | 当前状态 |
|------|-----------------|----------|----------|
| 风险审批 | 风险审批子域 spec | 审批对象 / 等级 / 触发 / 例外 / 决策记录 | 可在现有审批文档基础上收敛 |
| 运行中心 | 运行中心子域 spec | 任务生命周期、状态视图、任务编排（PromptDraft / StepPlan 结构与约束） | 已建立 v0.1：`docs/skillforge-run-center-domain-spec-v0.1.md`（待阶段 B 按 DoD 增补） |
| 对象追溯 | Registry 子域 spec | 核心对象唯一性、引用规则、跨域关系 | 已建立 v0.1：`docs/skillforge-registry-minimal-reference-rules-v0.1.md`（待阶段 B/C 增补） |
| 知识与资产 | 知识与资产子域 spec | 资产分类（Skeleton、模板片段）、版本化、复用规则、质量评分（阶段 D） | 已建立 v0.1：`docs/skillforge-knowledge-asset-domain-spec-v0.1.md`（待阶段 B 按 DoD 增补） |
| 系统与配置 | 系统与配置子域 spec | 配置分层、变更控制、安全边界 | 待启动 |

承载位不要求一开始就完整，但要求：
- 每个 spec 有明确 owner 域与完成定义（DoD）；
- 新能力在进入阶段实现之前，必须在对应 spec 中至少定义结构骨架（对象名、字段、约束、前后条件）；
- spec 之间如有交叉引用，必须注明引用来源与版本。

---

### 5.4 ADR（Architecture Decision Record）

职责：

- 记录关键架构/机制决策：背景、候选方案、取舍理由、影响范围；
- 为后续变更提供可追溯的决策依据。

触发场景（示例）：

- 跨模块接口范式变化；
- 数据模型核心字段或身份策略变化；
- 风险审批机制根策略调整。

---

### 5.5 Feature Truth

职责：

- 记录"某功能当前真实状态"：已实现、部分实现、未实现、风险与限制；
- 作为 roadmap 与对外沟通的事实基线，防止承诺漂移。

要求：

- 必须区分"已存在能力"与"计划能力"；
- 必须能链接到相关 spec/ADR/phase 证据。

---

### 5.6 Phase Report

职责：

- 记录阶段内实际推进：目标达成、偏差、风险、下一步调整；
- 作为路线回放与策略修正依据。

要求：

- 以结果与证据为中心，不做愿景重复；
- 必须指出对 roadmap 与文档体系的回写动作。

---

## 6. 更新规则：什么变化改哪类文档

1. **战略目标、边界、非目标变化**  
   → 更新产品总纲；必要时同步 roadmap 段落。

2. **页面结构、模块归属、导航逻辑变化**  
   → 更新 Web IA；若影响能力边界，同时更新相关子域 spec。

3. **单能力域规则变化（流程/状态/对象约束）**  
   → 更新对应子域 spec；若牵涉关键取舍，新增或更新 ADR。

4. **架构级关键决策变化**  
   → 必须更新 ADR；并在受影响 spec 中引用该 ADR。

5. **功能实现状态变化（完成/降级/回滚/受限）**  
   → 更新 feature truth；必要时在 phase 报告中说明原因与影响。

6. **阶段计划偏差、风险暴露、优先级调整**  
   → 更新 phase report，并回写 roadmap（如影响阶段目标）。

7. **仅实现细节变化但不影响产品语义**  
   → 可只在工程文档/代码注释更新，不强制回写产品总纲与 IA。

8. **任务编排对象（PromptDraft / StepPlan）的结构、约束或交互模型变化**  
   → 更新运行中心子域 spec；若变动影响 Skeleton 的步骤模板映射，同步更新知识与资产子域 spec；若涉及编排与审批的前后关系调整，需评估是否触发 ADR。

9. **Workflow Skeleton 的结构规范（要素定义 / 版本化 / 质量规则）变化**  
   → 更新知识与资产子域 spec；若骨架版本迭代导致 StepPlan 映射规则变化，需同步更新运行中心子域 spec 的编排映射章节；若涉及跨域对象引用策略变化，新增或更新 ADR。

10. **编排策略与 Skeleton 推荐从“人工”升级为“半自动 / 数据驱动”时**  
   → 必须新增 ADR（说明决策边界、人工兜底机制、数据依赖）；受影响子域 spec 需引用该 ADR；feature truth 需更新为“部分自动化（人工确认兜底）”而非“全自动”。

11. **模块从“已实现”推进到“已验证”，或仍停留在“代码已实现 / 分支已实现”时**  
   → 必须在产品总纲、Web IA、phase 报告或 truth 中显式区分“已实现 / 已验证 / 未验证”，禁止把空数据闭环、代码存在性或单分支实现混写成全量 happy path 验证完成。

## 7. 版本与废弃策略

### 7.1 版本标识

- 文档采用 `v主.次`（如 `v1.2`）：
  - 主版本：信息结构或治理规则发生重大变化；
  - 次版本：内容补充、表述澄清、轻度修订。
- 每次更新需附"更新摘要"（变更内容、影响范围、关联文档）。

### 7.2 生效与兼容

- 默认"最新稳定版生效"；
- 涉及迁移成本的重大变更需设置过渡窗口，并在 phase 报告中跟踪完成度。

### 7.3 废弃规则

- 不直接删除历史关键文档，标记为 `Deprecated` 并注明替代文档；
- 被废弃文档应保留：
  - 废弃原因；
  - 废弃日期；
  - 替代路径；
  - 仍受其影响的历史阶段范围。

### 7.4 一致性守护

- roadmap、feature truth、phase report 至少每阶段做一次一致性校验；
- 若出现冲突，以"最新 feature truth + ADR 决策"为事实优先，并触发相关文档修复。

## 8. 非目标

以下内容不属于本文档目标：

- 不给出逐周任务排期或个人级执行清单；
- 不把尚未验证的构想写成确定交付承诺；
- 不替代具体模块 spec、技术设计文档、测试方案；
- 不试图一次性冻结长期路线，允许按 phase 证据进行调整；
- 不以文档数量作为治理质量指标，重点是可追溯与一致性；
- 不承诺“自动 prompt 生成”或“自动步骤拆解”取代人工判断——编排层定位为辅助结构化与治理对象化，最终确认权始终在人工；
- 不把 Skeleton 的自动推荐与质量评分写成已实现——阶段 D 前仅作为方向性探索，实际交付节奏以各阶段退出条件为准；
- 不把“空数据闭环成立”写成“有业务样本的运行能力已全面验证完成”；
- 不把“代码分支已实现”写成“该分支 happy path 已被真实命令抽测覆盖”。
