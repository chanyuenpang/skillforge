# SkillForge 产品总纲(v1)

## 1. 产品定位

SkillForge 是一个面向"技能资产可信交付"的工程化产品:把技能从**定义、验证、运行、风险审查、审批发布到登记复用**串成一条可追溯链路。
它不是单点工具集合,也不是只服务某一个流程页面;它的核心价值是把"能跑"升级为"可审、可控、可复用"。

当前阶段,SkillForge 已具备较强的底层能力(契约验证、运行链路骨架、审查/审批事件模型、登记对象与持久化切面),并在 Web 端形成了风险审批子域的可用闭环。
因此,产品定位应从"风险审批网页"上收为"以风险治理为先导的技能生命周期平台",网页端则作为该平台的统一入口壳层逐步完善。

---

## 2. 目标用户与角色

SkillForge 面向"需要持续委派、协作与复盘 Agent 工作流"的团队,核心价值不是只展示风险,而是以治理优先方式让任务规范、执行过程与技能资产都可沉淀、可复用、可审计。

1. **Orchestrator / 主 Agent 使用者(负责人)**
   负责定义任务目标、拆分执行、派发 subagent,并对交付质量负责。核心诉求是让任务派发从"临时描述"升级为"可执行规范"。

2. **Subagent 执行者(含自动化子代理)**
   按任务规范完成具体步骤,产出可验收结果。核心诉求是减少目标歧义和返工。

3. **Workflow Designer(流程 / 方法维护者)**
   沉淀可复用 workflow skeleton,保证跨任务、跨场景的计划结构稳定。

4. **运行操作者(Operator)**
   负责触发运行、查看结果、跟踪执行证据,关注 Run 状态与异常信号。

5. **风险审查者(Reviewer)**
   对风险事实进行审查并给出 review 决策,关注证据充分性与审查轮次一致性。

6. **审批者(Approver)**
   对进入审批门的对象进行最终放行 / 驳回,关注合规、责任边界与审计留痕。

7. **资产管理员(Registry Steward)**
   负责登记资产质量与可检索性,维护 Registry 的发布秩序与可回溯性。

8. **产品 / 平台负责人(Owner)**
   关注端到端效率、风险敞口、交付稳定性与阶段性指标达成。

### 长期应用场景(产品总纲级)

1. **subagent 任务 prompt 优化 / 步骤化编排**:将主 agent 的原始派发说明转化为包含目标、上下文、约束、步骤、验收标准的任务规范,作为治理对象进入后续追踪。
2. **workflow skeleton 辅助结构化计划制定**:将历史有效模式提炼为 skeleton,辅助主 agent 在新任务中生成结构更清晰、拆解更稳定的计划。

## 3. 核心对象模型

SkillForge 的产品边界由对象模型定义,而非由单个页面定义。除 Skill / Fixture / Run / Risk / Approval / Registry 这条既有治理主链外,本阶段还需要显式纳入"任务规范化"与"计划结构化"两类长期能力对象。

### 3.1 Skill
技能能力本体,描述"做什么、如何做、边界是什么"。
它是整个链路的源头对象,承载能力声明与契约约束。

### 3.2 Fixture
Skill 的可验证样本与输入约束载体,用于稳定复现实验与回归。
Fixture 不是演示材料,而是运行与审查的共同证据入口。

### 3.3 Task Prompt Spec / PromptDraft
由原始 subagent 派发描述结构化后的任务规范对象,最小字段包括:目标(Goal)、上下文(Context)、约束(Constraints)、步骤(Steps)、验收标准(Acceptance)。
在调用点 B(派发 subagent)时作为输入的一部分被记录,出现在 Run Center 的 run 详情中。不作为独立流水线步骤,而是每次 spawn 时自然携带的上下文。

### 3.4 Skeleton(别名:Workflow Skeleton / Plan Template)
从稳定成功案例中抽取的计划骨架对象。在调用点 A(创建 plan)时作为模板提供给主 agent,辅助生成结构更清晰、边界更稳定的 plan。
不是具体计划实例,而是跨任务、跨场景可复用的方法模板。

### 3.5 Run(ExecutionRun 为实现层命名)
一次实际执行(或受控执行)记录,包含运行选择、状态、结果与证据引用。
Run 连接"定义世界"和"事实世界",是后续 Risk 判断的直接输入。

### 3.6 Risk
由运行事实与规则评估产生的风险事实层,表达风险等级、触发原因与处理建议。
Risk 对象负责把技术结果转译为治理信号,驱动 Review/Approval 的门控流程。

### 3.7 Approval
对需要治理决策的对象进行可审计决断的对象层,明确"谁在何时基于何依据做了什么决定"。
Approval 不是 UI 按钮动作,而是治理语义与责任归属的正式记录。

### 3.8 Registry
通过治理门控后进入可检索、可分发、可追溯的资产登记层。
Registry 是"可复用交付"的起点,不等同于"所有已运行对象"。

> 说明:Task Prompt Spec、PromptDraft、StepPlan、Skeleton 是"已建立定义骨架的核心能力对象"。Run Center 统一观测 plan 记录和 run 记录。审批(Approval)只在新建/注册技能写入仓库时触发,不在日常链路中。

## 4. 产品架构:两个独立拦截点 + 统一观测面

SkillForge 不是一条串联流水线。它是一个**无侵入的记录与增强层**,在两个独立调用点提供服务:

### 调用点 A:创建 plan
主 agent 创建计划时,SkillForge 提供 **workflow skeleton**(流程骨架:阶段拆解 / 步骤模板)。
- 输入:任务目标、上下文
- 输出:结构化 plan 骨架
- Run Center 记录:plan 输入输出 + skeleton 结构

### 调用点 B:派发 subagent
主 agent 派发子任务时,SkillForge 提供**拼接好的完整 skill + prompt**(可执行指令)。
- 输入:完整的 skill 定义 + 任务 prompt
- 输出:subagent 执行结果
- Run Center 记录:run 输入输出 + 可关联的 planRef

### 两个调用点之间的关系
- **相互独立**:可以在不创建 plan 的情况下直接 spawn subagent
- **可选关联**:如果 spawn 属于某个 plan,通过 planRef 关联
- **只记录,不阻断**:SkillForge 在每次调用时记录输入输出,但不做门控审批

### 统一观测面:Run Center
Run Center 是这两个拦截点的统一观测入口:
- Plan 记录:骨架结构、输入输出
- Run 记录:skill+prompt 输入、执行结果、planRef 关联

### 审批:特例,不是常态
审批只在**新建技能 / 注册技能写入仓库**时触发,是低频的门控动作,不在日常高频链路中。

## 5. 当前状态、阶段边界与下一阶段边界

### 5.1 当前状态(截至阶段一联调)

SkillForge 阶段一已形成可演示的产品面,当前信息架构与核心入口如下:

1. **顶层导航共存**:总览、风险审批、运行中心、知识资产、设置五个入口已在同一壳层下共存。
2. **风险审批既有闭环保持可用**:审批队列、详情、历史与审批动作仍可正常访问,且未因新增模块引入路由冲突。
3. **运行中心已完成第一刀**:
   - 前端路由:`/run-center`、`/run-center/runs`、`/run-center/runs/:runId`
   - 后端接口:`/api/run-center/*` 已存在
   - 当前 execution-log 为空,已验证"**空数据闭环**"成立,即页面、接口与状态处理链路可跑通,但不宣称有数据 happy path 已全面验证。
4. **知识资产已完成第一刀**:
   - 前端路由:`/knowledge-assets`、`/knowledge-assets/:assetId`
   - 后端接口:`/api/knowledge-assets*` 已存在
   - 当前白名单来源:`docs/` + `fixtures/`
   - doc 详情 happy path 已实测;skill-fixture 详情分支代码已实现,但未单独追加第二条命令样例抽测。
5. **当前事实判断**:产品已从"纯规划态"进入"可演示 + 可联调"的实现态,但第二阶段增强能力尚未展开。

### 5.2 当前阶段(已成立边界)

#### In Scope(已落地 / 已验证)

1. 顶层导航共存与模块入口打通(总览、风险审批、运行中心、知识资产、设置)。
2. 风险审批子域继续保持可操作闭环。
3. 运行中心基础路由与后端接口存在性打通,空数据场景可闭环。
4. 知识资产基础路由与后端接口存在性打通,doc 详情 happy path 可用。
5. 统一壳层下新增模块与既有审批模块未出现明显路由冲突。

#### Out of Scope(本阶段未承诺)

1. 运行中心"有数据"丰富样本与大规模历史运行分析能力。
2. skill-fixture 详情路径的完整实测覆盖(当前为代码实现到位,但抽测未补齐)。
3. 第二阶段能力(如跨项目聚合、复杂治理自动化等)不在本次边界内。
4. 写操作、治理状态流转与高级策略化能力不属于阶段一交付范围。

### 5.3 下一阶段(应达成边界)

1. **第一单真实任务全链路可观测**:两个拦截点(plan 创建 / subagent 派发)各自记录输入输出,Run Center 可追溯全链路。
2. **Run Center 从空壳走向有数据**:plan 记录和 run 记录在 Run Center 可观察。
3. **建立基础可追溯率基线**:统计日常任务中从派发到验收具备完整轨迹的比例。
4. **从"可演示"走向"可运营"**:形成更稳定的样本验证与事实层更新机制。

---

## 6. 非目标

本总纲明确以下事项不在当前产品承诺范围内:

1. 不宣称所有底层预留能力已经产品化落地。
2. 不在当前阶段追求完整平台化大而全体验。
3. 不以重做风险审批逻辑替代产品壳层建设。
4. 不将实验性/占位性能力包装为稳定生产能力。
5. 不绕开治理门控直接把运行结果等同于可发布资产。
6. 不把"运行中心空数据闭环成立"表述为"运行数据能力已被丰富样本全面验证"。
7. 不把"skill-fixture 详情分支代码已实现"表述为"skill-fixture happy path 已实测完成"。

---

## 7. 阶段成功指标

v1 阶段成功不仅看"产品壳层成立 + 治理链可追溯",也要看"任务规范化"与"计划结构化"是否真的改善交付质量。建议按能力成熟度递进设定指标:

### 阶段 A:可用性建立(先把对象跑通)

- **Task Prompt Spec 覆盖率**:进入 subagent 派发的任务中,具备目标 / 上下文 / 约束 / 步骤 / 验收标准五要素的比例。
- **Workflow Skeleton 使用率**:计划制定时引用 workflow skeleton 的任务占比。
- **基础可追溯率**:任务从派发到验收具备完整执行轨迹的比例。

### 阶段 B:质量改进(证明方法有效)

- **一次验收通过率**:按验收标准一次通过的任务比例。
- **返工率下降**:因任务描述不清或计划结构不稳导致的返工占比下降。
- **拆解稳定度**:同类任务在阶段划分与步骤顺序上的一致性提升。

### 阶段 C:治理闭环(形成长期资产)

- **高质量 Task Prompt Spec 复用率**:被二次以上复用且仍保持通过率的规范占比。
- **Workflow Skeleton 演进效率**:骨架版本迭代后带来的通过率提升或返工率下降。
- **治理决策有效性**:被限制 / 修订 / 冻结对象的后续风险事件下降。

> 指标定位:用于验证两项长期场景(Task Prompt Spec 化、Workflow Skeleton 引导)对交付质量与治理闭环的真实贡献,而非仅衡量文档产出数量。

---

SkillForge v1 的关键不是"页面数量增加"，而是建立一个可信的记录与观测骨架：  
**每一次 plan 创建、每一次 subagent 派发，都在 Run Center 留下可追溯的记录。在可观测的基础上，逐步沉淀可复用的技能和计划方法。**
